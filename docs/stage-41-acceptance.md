# 第 41 阶段验收：前端成果接收清单

## 本阶段目标

本阶段整理前端工作台的成果接收清单，把业务链路、管理端排查、压测记录和压测对比串成一套可以手动验收、演示和复述的脚本。

这一阶段要让你明确看到：

- 你不是只在旁边看代码完成，而是能按清单接收成果。
- 每个页面区域都对应一个后端能力或项目展示目标。
- 接收时要记录 `orderId`、`ticketCode`、状态、traceId 和压测指标。
- 面试展示要按“业务链路 -> 后台排查 -> 压测证据”来讲。

## 接收清单覆盖范围

`docs/frontend-acceptance-demo-script.md` 覆盖：

| 模块 | 接收目标 |
| --- | --- |
| 接收前准备 | 知道如何启动后端和前端 |
| 活动与票档 | 确认活动、场次、票档和库存能展示 |
| 同步抢票 | 确认能创建 `PENDING_PAYMENT` 订单 |
| 支付出票 | 确认订单变为 `PAID` 并生成 `VALID` 电子票 |
| 查询与验票 | 确认电子票能从 `VALID` 变为 `VERIFIED` |
| 管理端排查 | 确认后台能按用户、订单、票码反查数据 |
| 压测结果记录 | 确认能记录 QPS、P95、P99 和是否超卖 |
| 压测对比展示 | 确认默认方案和 Redis Lua 方案能同口径对比 |
| 演示脚本 | 提供一套面试或项目展示时的讲述顺序 |
| 接收记录表 | 提供手动记录 `orderId`、`ticketCode` 和结论的位置 |

## 本阶段边界

本阶段暂不做：

- 新增页面功能。
- 自动录制演示视频。
- 自动生成压测报告。
- 安装 UI Skill。

当前先把成果接收流程固定下来，后续做视觉升级或 Skill 安装时，才不容易偏离项目主线。

## 你需要学会的点

- 接收项目成果时，要按步骤验证，不是只看“页面能打开”。
- 验收要记录关键变量：`userId`、`orderId`、`ticketCode`、状态、traceId。
- 面试展示要先讲业务闭环，再讲后台排查，最后讲压测证据。
- 文档本身也是项目交付的一部分。

## 面试表达

可以这样说：

> 我给前端工作台整理了成果接收清单。它不是单纯的使用说明，而是把活动查询、抢票、支付、出票、验票、管理端排查和压测证据串成一套验收脚本。每一步都明确要看什么状态、记录什么变量、面试时怎么解释，保证项目成果能被复现和复述。
