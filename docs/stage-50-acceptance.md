# Stage 50 验收：售罄候补购票

## 做了什么

- 新增持久化候补记录和购票人脱敏快照，状态为 `WAITING`、`FULFILLED`、`CANCELED`、`EXPIRED`。
- 票档库存不足或已有等待队列时，用户可提交 1 到 5 人整单候补，并查看前方等待笔数。
- 退款、部分退票和订单超时取消释放库存后，在原事务提交后触发候补兑现。
- 兑现严格按提交顺序处理；库存不能覆盖队首全部购票人时不拆单，也不让后来的小单跳队。
- 兑现成功生成 `PENDING_PAYMENT` 订单，候补记录返回 `orderId` 和支付截止时间。
- 前端售罄票档显示“可候补”，提交前核对购票人与兑现后金额；“我的电子票”中可查看、取消候补或打开兑现订单。

## 你该学会什么

1. 异步抢票解决请求削峰，候补解决无库存后的长期排队，两者不能混成同一个状态模型。
2. 公平队列不仅是按时间排序，还要防拆单、跳队和重复兑现。
3. 退款事务应该先完成，再触发候补建单；候补失败不能把用户已完成的退款一起回滚。
4. 数据库唯一键保护单用户活跃候补，队首锁和状态条件更新保护并发兑现。
5. 候补成功不等于出票，必须经过“等待 -> 兑现为待支付订单 -> 支付 -> 出票”。

## 自动验收

```powershell
mvn test
cd frontend
npm.cmd run build
```

自动化测试覆盖：库存足够时拒绝候补、售罄入队、重复候补、前方笔数、多人不拆单、队首兑现、生成待支付订单、重复触发、取消、越权、场次开始过期、统一响应和 `traceId`。

## 页面验收

1. 打开“车票预订”，把某票档库存用完后刷新。
2. 选择显示“可候补”的票档，填写购票人并点击“核对候补”。
3. 确认页面明确提示“候补成功不等于出票”，金额标题为“兑现后应付”。
4. 提交后确认页面显示 `waitlistId`、前方笔数、整单人数、金额和 `traceId`。
5. 打开“我的电子票”，确认“我的候补”显示排队状态并可取消。
6. 让已支付订单退票释放库存，刷新候补；库存足够时状态应变为“已兑现”。
7. 点击“查看待支付订单”，确认回到支付区并可继续支付出票。

## 面试表达

> 我没有把候补复用成异步抢票。异步抢票是请求进来后立即尝试扣库存，候补则是库存不足后的持久等待。候补兑现用数据库队首锁和状态条件更新防重复，并要求库存能覆盖整组购票人；退款和超时取消提交后再触发兑现，避免候补异常影响原交易结果。
