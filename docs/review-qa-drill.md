# EventRush 项目复盘问答训练

这份文档不是完整面试题库，而是训练你“开口讲项目”的短问短答卡片。每个问题都按一个固定结构来练：

```text
问题是什么 -> 我怎么设计 -> 项目里怎么落地 -> 怎么验证
```

真正面试时不要死背整段话，而是先记住关键词，再按现场问题展开。

## 练习方法

建议每次只练 6 个问题：

1. 先看问题，不看答案，自己说一遍。
2. 再看关键词，确认有没有漏掉核心点。
3. 最后看参考回答，把自己的表达补完整。

每个回答尽量控制在 30 秒到 60 秒。面试官追问时，再展开代码、测试和文档落点。

## 1. 这个项目一句话怎么介绍？

### 关键词

高并发票务、抢票、支付、验票、库存一致性、幂等、MQ、Redis Lua、接口治理。

### 参考回答

EventRush 是一个高并发活动票务后端项目，模拟用户抢票、支付出票、电子票核验和后台查询。它的重点不是普通 CRUD，而是围绕抢票场景处理库存一致性、防重复抢票、支付幂等、订单超时取消、消息消费幂等、Redis Lua 原子扣库存、统一响应和 traceId 排查。

### 展开追问

- 如果面试官问“你主要负责什么”，就讲阶段推进和核心链路。
- 如果面试官问“为什么做这个项目”，就讲高并发业务训练价值。

## 2. 项目的完整业务链路是什么？

### 关键词

查活动、选场次票档、抢票、待支付订单、支付、电子票、验票、后台查询。

### 参考回答

用户先查询活动列表和活动详情，选择场次和票档后调用抢票接口。抢票成功会生成待支付订单并扣减库存；用户支付后订单变为已支付，同时生成电子票。入场时工作人员通过票码核验电子票，核验成功后票状态变为已核验。管理端可以按用户、订单和票码查询数据，方便排查。

### 展开追问

- 如果问“为什么支付后才出票”，强调电子票是入场凭证，不能给未支付用户。
- 如果问“订单和电子票怎么分工”，强调订单管交易状态，电子票管入场凭证。

## 3. 抢票为什么会超卖？

### 关键词

并发、先查再改、非原子、多个请求看到同一份库存。

### 参考回答

超卖本质是并发竞争。如果多个请求同时查到库存大于 0，然后都继续扣库存，就可能卖出超过库存数量的票。所以抢票不能简单写成“查库存 -> 判断 -> 扣库存”，库存检查和扣减必须在同一个并发控制边界里完成。

### 展开追问

- 如果问“怎么解决”，讲数据库扣减、唯一约束和 Redis Lua。
- 如果问“怎么验证”，讲并发测试和压测成功数不能超过库存。

## 4. 项目怎么防止超卖？

### 关键词

基础正确性、数据库库存扣减、重复订单保护、Redis Lua 原子执行。

### 参考回答

项目先保证基础正确性：内存版用同步逻辑控制库存，持久化版通过数据库库存扣减和订单创建规则保证不超卖。进阶方案里使用 Redis Lua，把库存检查、重复用户检查、扣减库存和记录用户放在同一个脚本里执行，避免多次 Redis 调用之间被其他请求插入。

### 展开追问

- 如果问“Redis Lua 返回值”，说明 `-1` 库存不足、`-2` 重复抢票、`-3` 库存未初始化。
- 如果问“为什么还要数据库兜底”，强调 Redis 是预扣减，最终订单仍要落库。

## 5. 为什么要防重复抢票？

### 关键词

公平性、同一用户同一票档、重复订单、Redis Set、数据库约束。

### 参考回答

抢票场景里，同一用户同一票档通常只允许抢一次，否则会影响公平性，也可能导致订单数据混乱。项目里在业务层判断用户是否已经有对应订单，Redis Lua 方案里用 Set 记录抢过的用户，数据库层也通过唯一规则做兜底。

### 展开追问

- 如果问“只靠前端按钮禁用行不行”，回答不行，后端必须兜底。
- 如果问“重复抢票返回什么”，讲统一错误响应。

## 6. Redis Lua 为什么能保证原子性？

### 关键词

Redis 单线程执行脚本、脚本期间不中断、多步操作一次完成。

### 参考回答

Lua 脚本会在 Redis 内部作为一个整体执行。脚本执行期间，不会穿插其他客户端命令，所以可以把库存检查、用户重复检查、库存扣减和用户记录合成一次原子操作。这样比多次 Redis 调用更适合抢票这种并发竞争场景。

### 展开追问

- 如果问“Lua 解决所有一致性问题吗”，回答不能，它解决 Redis 内部原子性，最终订单落库仍要保证一致。
- 如果问“本地默认开吗”，回答默认关闭，通过 `eventrush.stock.redis-enabled=true` 开启。

## 7. 为什么抢票成功后先生成待支付订单？

### 关键词

资格锁定、交易未完成、支付后出票、超时释放。

### 参考回答

抢票成功只是用户拿到了购买资格，交易还没完成，所以先生成待支付订单。只有支付成功后才生成电子票。如果用户超时未支付，订单会被取消，库存会释放。这样订单负责交易状态，电子票负责入场凭证，职责比较清楚。

### 展开追问

- 如果问“库存什么时候释放”，讲超时取消和取消时释放库存。
- 如果问“已支付订单能取消吗”，讲状态判断。

## 8. 订单超时取消怎么保证不误取消？

### 关键词

延时消息只是提醒、先查状态、只取消待支付、定时扫描兜底。

### 参考回答

订单创建后会发送延时消息。消息到期后消费者不会直接取消订单，而是先查订单当前状态，只有仍然是待支付才取消并释放库存。如果订单已经支付，就不会取消。项目还保留定时扫描作为兜底，避免 MQ 不可用时订单一直占用库存。

### 展开追问

- 如果问“为什么不能直接取消”，强调消息到达时状态可能已经变化。
- 如果问“MQ 重复消费怎么办”，强调状态判断天然幂等。

## 9. 支付幂等怎么做？

### 关键词

重复点击、网络重试、订单状态、已有电子票、唯一约束。

### 参考回答

支付请求可能重复到达，所以支付接口必须幂等。项目里只有待支付订单能流转到已支付并生成电子票；如果订单已经支付，再次支付会返回已有电子票，不会生成第二张。数据库里电子票和订单也有唯一关系作为兜底。

### 展开追问

- 如果问“幂等是不是拒绝重复请求”，回答不是，是重复请求不产生重复业务结果。
- 如果问“取消订单还能支付吗”，回答不能。

## 10. MQ 消息重复消费怎么办？

### 关键词

至少一次投递、消费者幂等、请求状态、订单状态。

### 参考回答

消息队列一般要按至少一次投递来设计，所以消费者不能假设消息只来一次。异步抢票消息会根据请求状态判断是否已经处理过，避免重复创建订单；订单超时消息会先查订单状态，只取消待支付订单。这样即使重复消费，也不会重复处理业务结果。

### 展开追问

- 如果问“为什么不用 MQ 保证绝对一次”，回答业务侧仍然必须做幂等。
- 如果问“怎么排查重复消息”，讲请求状态和 traceId。

## 11. RocketMQ 在项目里解决什么？

### 关键词

异步抢票、削峰、订单超时、延时消息、解耦。

### 参考回答

RocketMQ 主要用在两处。第一是异步抢票，接口先保存请求并返回 requestId，后续由消费者处理抢票逻辑；第二是订单超时取消，订单创建后发送延时消息，到期后检查并取消待支付订单。它的作用是削峰、解耦和处理延时任务。

### 展开追问

- 如果问“MQ 不可用怎么办”，讲配置开关和兜底扫描。
- 如果问“为什么本地默认不开”，讲降低学习环境依赖。

## 12. traceId 的价值是什么？

### 关键词

响应头、响应体、日志、一次请求、排查问题。

### 参考回答

traceId 用来把一次请求的响应和服务端日志关联起来。项目里如果请求带了 `X-Trace-Id` 就沿用，没有就生成新的；它会写入响应头、统一响应体和日志。联调或排查问题时，可以拿 traceId 快速定位对应日志。

### 展开追问

- 如果问“它是不是分布式链路追踪”，回答当前是轻量版，后续可接入 SkyWalking 或 OpenTelemetry。
- 如果问“为什么响应体也放”，回答方便前端或调用方直接读取。

## 13. 统一响应有什么价值？

### 关键词

前端解析一致、错误码、message、data、traceId。

### 参考回答

统一响应让调用方不用为每个接口写不同解析逻辑。项目里成功和失败都会返回统一结构，包括 `success`、`code`、`message`、`data` 和 `traceId`。这样前端能统一判断成功失败，后端也能通过错误码和 traceId 辅助排查。

### 展开追问

- 如果问“HTTP 状态码还要不要”，回答要，HTTP 状态码和业务 code 分别表达不同层面的结果。
- 如果问“校验错误怎么处理”，讲统一异常处理。

## 14. 管理端为什么要鉴权？

### 关键词

后台数据、订单、票码、只读也敏感、环境变量配置。

### 参考回答

管理端能查询用户订单和电子票信息，即使是只读接口也不能公开访问。项目里用 `X-Admin-Key` 对 `/api/admin/**` 做轻量保护，并支持通过环境变量覆盖默认密钥。后续如果项目继续扩展，可以替换成登录、JWT 或 RBAC。

### 展开追问

- 如果问“为什么不是完整权限系统”，回答当前阶段用最小方案覆盖权限边界。
- 如果问“密钥写死有什么问题”，回答代码推到仓库后会暴露。

## 15. 压测时你重点看什么？

### 关键词

正确性优先、不超卖、成功数、失败数、QPS、P95、P99、同参数对比。

### 参考回答

抢票压测首先看正确性，成功数不能超过库存，失败原因要符合预期。然后再看性能指标，比如 QPS、平均耗时、P95、P99。对比默认方案和 Redis Lua 方案时，必须使用相同并发数、请求数、票档和用户范围，否则结果没有可比性。

### 展开追问

- 如果问“本地压测能代表生产吗”，回答不能，只能作为学习基线。
- 如果问“为什么写压测报告”，回答让结果可复盘、可展示。

## 16. 项目还有哪些不足？

### 关键词

真实 MySQL、登录权限、生产级压测、库存对账、消息轨迹、监控告警。

### 参考回答

目前项目已经覆盖了核心后端场景，但仍然有提升空间。比如把本地 H2 切到 MySQL 做更真实的事务验证，引入登录和 RBAC 替代简单管理密钥，补充更完整的压测环境和报告，增加库存对账、消息消费记录、监控告警和链路追踪。

### 展开追问

- 如果问“你会先做哪个”，优先说 MySQL 联调和更完整的压测，因为它们最能验证业务正确性。
- 如果问“现在为什么没做”，回答当前阶段先保证核心链路和学习成本可控。

## 30 秒背诵版

> EventRush 是一个高并发票务后端项目，完整实现活动查询、抢票、支付出票、验票和后台查询。项目重点解决抢票里的库存一致性、防重复抢票、支付幂等、订单超时取消和消息消费幂等。Redis Lua 用来把库存检查、重复用户检查和扣库存做成原子操作，RocketMQ 用来做异步抢票和延时取消。接口层统一响应并返回 traceId，方便联调和排查。压测时先验证不超卖，再看 QPS、P95 和 P99。

## 你真正要练到什么程度

练到这一步就算过关：

- 能 1 分钟讲清楚项目主线。
- 能 30 秒讲清楚 Redis Lua 的价值。
- 能 30 秒讲清楚 MQ 重复消费和订单超时取消。
- 能说出至少 3 个项目不足和下一步优化方向。
- 能把每个技术点都落回“抢票业务问题”，而不是只报技术名词。
