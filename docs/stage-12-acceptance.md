# 第 12 阶段验收：支付幂等和电子票防重复生成

## 本阶段交付

- 支付接口 `POST /api/orders/{orderId}/pay` 支持幂等。
- 同一个订单第一次支付会生成电子票。
- 同一个订单重复支付时，不会再次生成电子票，而是返回已有电子票。
- 数据库继续通过 `electronic_ticket.order_id` 唯一约束兜底，保证一个订单最多只有一张电子票。
- 内存版本和数据库版本都补了测试。

## 为什么要做这一阶段

真实支付链路里，重复请求很常见：

- 用户重复点击支付按钮。
- 前端请求超时后重试。
- 支付平台回调重复发送。
- 服务之间调用失败后自动重试。

如果支付接口不幂等，重复请求可能导致同一个订单生成多张电子票。现在的规则是：一个订单支付成功后，再次支付同一个订单，返回第一次生成的电子票。

## 当前规则

```text
PENDING_PAYMENT + 支付请求 -> PAID + 生成电子票
PAID + 重复支付请求 -> 返回已有电子票
CANCELED + 支付请求 -> 拒绝支付
```

电子票表里已经有两个关键唯一约束：

- `order_id` 唯一：一个订单只能有一张电子票。
- `ticket_code` 唯一：一个票码只能对应一张电子票。

## 手动验收

启动应用：

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=18086"
```

先抢票生成订单：

```http
POST http://localhost:18086/api/orders/grab
Content-Type: application/json

{
  "userId": 9700,
  "sessionId": 101,
  "ticketCategoryId": 1001
}
```

第一次支付：

```http
POST http://localhost:18086/api/orders/把这里换成订单id/pay
```

第二次重复支付：

```http
POST http://localhost:18086/api/orders/把这里换成同一个订单id/pay
```

预期：

- 两次支付返回的 `id` 一样。
- 两次支付返回的 `ticketCode` 一样。
- 订单状态保持 `PAID`。
- 不会生成第二张电子票。

## 你需要学会的点

- 幂等不是“不让用户重复请求”，而是“重复请求不会造成重复业务结果”。
- 支付、发券、发票、发货这类链路都必须重点考虑幂等。
- 代码层通过订单状态判断，数据库层通过唯一约束兜底。
- 比起新增复杂的幂等表，本阶段直接复用订单状态和电子票唯一约束，成本更低，也足够覆盖当前项目。

## 面试表达

可以这样说：

> 我对支付接口做了幂等处理。订单第一次支付时，只有 PENDING_PAYMENT 状态能流转到 PAID 并生成电子票；如果同一个订单已经是 PAID，再次支付会直接查询并返回已有电子票。同时电子票表对 order_id 建了唯一约束，保证数据库层也不会出现一个订单多张票的问题。
