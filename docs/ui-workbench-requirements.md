# EventRush 前端工作台需求设计

这份文档承接 `docs/product-output-blueprint.md`，把“高并发票务操作工作台”拆成第一版前端可以实现的页面、接口、状态和验收标准。

本阶段仍然不写 UI 代码。先把需求定清楚，是为了保证后续页面不是凭感觉做出来的，而是能准确展示后端能力、业务链路和数据证据。

## 设计原则

第一版前端必须服务于项目展示和验收，而不是做成普通票务商城。

核心原则：

- 第一屏就是可操作工作台，不做营销首页。
- 页面要展示业务状态，不隐藏订单、票码、traceId、错误码。
- 普通用户、验票人员、管理人员三种视角都要能跑通。
- 压测证据先做“记录和展示”，后续再做自动采集。
- 不引入复杂登录注册，管理端继续使用 `X-Admin-Key`。
- 不为了视觉效果牺牲可读性和验收效率。

## 第一版范围

### 必须做

| 模块 | 目标 | 验收标准 |
| --- | --- | --- |
| 活动浏览 | 看到活动、场次、票档和库存 | 能从 `GET /api/events` 渲染活动和票档 |
| 抢票操作 | 输入用户 ID 后发起同步抢票 | 成功后展示 `orderId` 和 `PENDING_PAYMENT` |
| 异步抢票 | 发起异步抢票并查询结果 | 展示 `requestId`、处理中、成功或失败 |
| 支付出票 | 对订单执行支付 | 成功后展示 `ticketCode` 和 `VALID` |
| 电子票查询 | 根据票码查询票状态 | 展示票码、订单 ID、票状态 |
| 验票 | 验票人员输入票码核验 | 成功后票状态变为 `VERIFIED`，重复验票有错误提示 |
| 管理查询 | 管理人员按用户、订单、票码排查 | 携带 `X-Admin-Key` 后能查询管理端接口 |
| 响应排查 | 展示每次请求的响应状态 | 展示 `success`、`code`、`message`、`traceId` |
| 压测证据 | 展示一次压测记录 | 可录入或展示 success、failed、QPS、P95、P99、是否超卖 |

### 暂不做

| 暂不做 | 原因 |
| --- | --- |
| 登录注册 | 当前重点不是账号系统，容易冲淡抢票主线 |
| 复杂角色权限 | 第一版用视图分区和 `X-Admin-Key` 足够验收 |
| 座位图 | 会引入大量票务细节，不是当前高并发重点 |
| 支付网关 | 当前是模拟支付，重点是支付后出票和幂等 |
| 自动监控大屏 | 后端还没有指标采集接口，先做压测记录展示 |
| 移动端深度适配 | 第一版以桌面工作台演示为主，保证基础响应式即可 |

## 页面结构

建议第一版做成一个工作台页面，使用顶部身份切换或左侧导航分区。

```text
EventRush 工作台
├─ 概览区
│  ├─ 当前服务地址
│  ├─ 当前用户 ID
│  ├─ 最近 orderId
│  ├─ 最近 ticketCode
│  └─ 最近 traceId
├─ 用户抢票区
│  ├─ 活动与票档
│  ├─ 同步抢票
│  ├─ 异步抢票
│  ├─ 订单支付
│  └─ 电子票
├─ 验票区
│  ├─ 票码输入
│  ├─ 核验按钮
│  └─ 核验结果
├─ 管理查询区
│  ├─ 管理端密钥
│  ├─ 按用户查订单
│  ├─ 按订单查票
│  └─ 按票码查票
└─ 证据区
   ├─ 最近请求记录
   ├─ 错误和 traceId
   └─ 压测结果摘要
```

## 业务流程

### 普通用户链路

```text
查询活动 -> 选择场次和票档 -> 输入 userId -> 抢票 -> 获得 orderId -> 支付 -> 获得 ticketCode -> 查询电子票
```

页面必须让用户明确看到：

- 当前选择的是哪个 `sessionId`。
- 当前选择的是哪个 `ticketCategoryId`。
- 抢票成功后订单状态是 `PENDING_PAYMENT`。
- 支付成功后订单状态变成 `PAID`。
- 电子票初始状态是 `VALID`。

### 验票人员链路

```text
输入 ticketCode -> 查询电子票 -> 核验电子票 -> 展示 VERIFIED 或错误提示
```

页面必须让验票人员明确看到：

- 票是否存在。
- 票是否有效。
- 票是否已经核验过。
- 核验人员 `verifierId`。

### 管理人员链路

```text
输入 X-Admin-Key -> 按用户查订单 -> 按订单查票 -> 按票码查票 -> 结合 traceId 排查问题
```

页面必须让管理人员明确看到：

- 当前管理端密钥是否已填写。
- 401 是鉴权失败，不是系统异常。
- 用户订单列表。
- 订单对应电子票。
- 票码详情。

## 接口映射

| UI 动作 | 方法 | 接口 | 输入 | 成功后展示 |
| --- | --- | --- | --- | --- |
| 加载活动 | GET | `/api/events` | 无 | 活动、场次、票档、库存 |
| 查询活动详情 | GET | `/api/events/{eventId}` | `eventId` | 单个活动详情 |
| 同步抢票 | POST | `/api/orders/grab` | `userId`、`sessionId`、`ticketCategoryId` | `orderId`、订单状态 |
| 异步抢票 | POST | `/api/orders/grab-async` | `userId`、`sessionId`、`ticketCategoryId` | `requestId`、请求状态 |
| 查询异步结果 | GET | `/api/orders/grab-requests/{requestId}` | `requestId` | 处理状态、订单 ID 或失败原因 |
| 支付订单 | POST | `/api/orders/{orderId}/pay` | `orderId` | `ticketCode`、票状态 |
| 查询订单 | GET | `/api/orders/{orderId}` | `orderId` | 订单详情、订单状态 |
| 查询电子票 | GET | `/api/tickets/{ticketCode}` | `ticketCode` | 票详情、票状态 |
| 核验电子票 | POST | `/api/tickets/verify` | `ticketCode`、`verifierId` | `VERIFIED` 状态 |
| 按用户查订单 | GET | `/api/admin/users/{userId}/orders` | `userId`、`X-Admin-Key` | 用户订单列表 |
| 按订单查票 | GET | `/api/admin/orders/{orderId}/ticket` | `orderId`、`X-Admin-Key` | 订单对应电子票 |
| 按票码查票 | GET | `/api/admin/tickets/{ticketCode}` | `ticketCode`、`X-Admin-Key` | 票码详情 |

## 状态展示规则

### 订单状态

| 状态 | 页面文案 | 操作 |
| --- | --- | --- |
| `PENDING_PAYMENT` | 待支付 | 可点击支付，可等待超时取消 |
| `PAID` | 已支付 | 可查看电子票，不再重复出票 |
| `CANCELED` | 已取消 | 不可支付，需要重新抢票 |

### 电子票状态

| 状态 | 页面文案 | 操作 |
| --- | --- | --- |
| `VALID` | 有效 | 可核验 |
| `VERIFIED` | 已核验 | 不可重复核验 |

### 异步抢票状态

具体字段以后端返回为准。页面至少要支持：

| 状态含义 | 页面文案 |
| --- | --- |
| 请求已提交 | 已提交 |
| 消费者处理中 | 处理中 |
| 抢票成功 | 抢票成功 |
| 抢票失败 | 抢票失败 |

如果后端返回字段命名与页面枚举不完全一致，前端应保留原始响应，同时映射成用户能看懂的状态文案。

## 错误提示规则

前端不能只弹出“请求失败”。必须把后端统一响应里的关键信息展示出来。

| 场景 | 后端表现 | 页面提示 |
| --- | --- | --- |
| 缺少字段 | `VALIDATION_ERROR` | 请检查必填项 |
| 库存不足 | `BUSINESS_ERROR` | 库存不足，本次抢票失败 |
| 重复抢票 | `BUSINESS_ERROR` | 该用户已经抢过该票档 |
| 重复验票 | `BUSINESS_ERROR` | 该电子票已核验，不能重复入场 |
| 管理端未授权 | `UNAUTHORIZED` | 管理端密钥错误或未填写 |
| 服务未启动 | 网络错误 | 请确认后端服务已启动 |

每次错误都要展示：

- `code`
- `message`
- `traceId`

## 最近请求记录

工作台需要保留最近若干次请求记录，方便演示和排查。

建议字段：

| 字段 | 说明 |
| --- | --- |
| 时间 | 请求发生时间 |
| 动作 | 例如抢票、支付、验票 |
| 方法 | GET / POST |
| 接口 | 请求路径 |
| 结果 | 成功 / 失败 |
| code | 后端响应码 |
| traceId | 链路编号 |
| 摘要 | 订单 ID、票码或错误信息 |

第一版可以只存在浏览器内存中，不需要持久化。

## 压测证据区

第一版前端不直接执行压测脚本，因为浏览器不适合控制本机 PowerShell 压测，也没有后端指标采集接口。

第一版建议做成“压测结果记录面板”：

| 字段 | 来源 |
| --- | --- |
| 压测模式 | 手动选择：默认 H2、本地 MySQL、Redis Lua、RocketMQ 异步 |
| Users | 从压测脚本参数填写 |
| 票档库存 | 从活动票档读取或手动填写 |
| success | 从脚本输出填写 |
| failed | 从脚本输出填写 |
| QPS | 从脚本输出填写 |
| avgMs | 从脚本输出填写 |
| p95Ms | 从脚本输出填写 |
| p99Ms | 从脚本输出填写 |
| 是否超卖 | 页面根据 success 和库存给出判断 |

判断规则：

```text
success <= 票档库存，则没有超卖
success > 票档库存，则疑似超卖，需要排查
```

后续可以升级为：

- 后端保存压测报告。
- 前端读取历史压测报告。
- 使用图表展示优化前后对比。
- 展示失败原因分布。

## 技术建议

第一版建议使用：

| 分类 | 建议 |
| --- | --- |
| 构建工具 | Vite |
| 前端框架 | Vue 3 |
| 请求库 | Axios 或原生 `fetch`，第一版都可以 |
| 图标 | lucide 图标库 |
| 图表 | 第一版可先不用，压测面板用数字摘要；后续再接 ECharts |
| 样式 | 普通 CSS 或轻量组件样式，不急着引入大型 UI 框架 |

建议先选择 Vue 3 + Vite。原因是学习成本适中，适合做操作工作台，也方便后续扩展组件。

## 第一版验收清单

完成 UI 后，至少要能手动验收下面内容：

1. 打开页面后自动加载活动列表。
2. 选择票档后能看到 `sessionId` 和 `ticketCategoryId`。
3. 输入 `userId` 后同步抢票成功，页面出现 `orderId`。
4. 点击支付后出现 `ticketCode`。
5. 查询电子票后状态为 `VALID`。
6. 核验后状态变为 `VERIFIED`。
7. 重复核验时页面展示业务错误和 `traceId`。
8. 管理端未填密钥时返回 401，并展示明确提示。
9. 填写正确 `X-Admin-Key` 后可以按用户、订单、票码查询。
10. 最近请求记录中能看到接口路径、结果和 `traceId`。
11. 压测证据区能填写一组压测结果，并判断是否超卖。

## 面试展示方式

打开前端时，建议按这个顺序演示：

1. 先展示活动和票档库存，说明业务模型。
2. 用一个用户抢票，说明防超卖入口。
3. 支付订单，说明订单状态机和支付幂等。
4. 展示电子票并验票，说明票和订单职责拆分。
5. 重复验票，说明边界错误处理。
6. 进入管理查询区，说明后台排查能力。
7. 展示 traceId 和最近请求记录，说明接口治理。
8. 展示压测证据区，说明项目优化不是空谈。

## 你需要学会的点

- 前端需求要从后端能力和验收目标倒推，不是先画页面。
- 工作台页面要暴露关键状态，方便讲清业务，而不是把所有技术细节藏起来。
- 管理端、验票端、用户端分别对应真实业务角色。
- 没有后端指标接口时，压测可视化第一版可以先做“结果记录”，后续再自动化。
- 第一版范围要克制，先跑通完整展示链路，再做视觉和工程优化。
