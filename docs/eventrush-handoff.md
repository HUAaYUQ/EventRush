## 1. 项目身份

EventRush 是一个面向真实演出票务场景的高并发票务平台，不是普通 CRUD，也不是只做页面展示的练习项目。

它需要逐步覆盖：活动发现、活动详情、场次选择、票档与库存、实名购票、订单、支付、退票退款、电子票、主办方发布、内容治理、验票入场和高并发系统能力。

产品参考 12306、大麦等成熟票务平台，但不复制它们的视觉，也不把成熟平台的复杂功能无条件堆进项目。EventRush 的核心判断是：

购票平台出现的每一项内容，都必须能追溯到后台的配置、审核、发布和责任边界。

## 2. 当前产品结构

系统由两个主要平台组成。

### 2.1 购票平台

服务普通购票用户，用户只需要一个统一入口完成以下事情：

- 浏览首页活动和运营内容
- 按城市、类目、时间和关键词寻找活动
- 阅读活动详情、场次、价格和观演规则
- 选择场次、票档或座位
- 填写实名观演人并提交订单
- 完成支付并查看订单状态
- 获取和使用电子票
- 办理退票、退款和售后
- 查看个人订单、收藏、提醒和观演记录

购票端不把主办方工具、压力测试、工程证据和验票后台混入普通用户导航。验票和工程证据当前暂缓，后续作为独立后台能力进入系统。

### 2.2 主办方工作台

服务活动主办方和平台运营人员，是购票平台的内容和售票控制中心。

工作台负责：

- 活动创建和基础定位
- 活动类目和内容类型
- 活动封面、详情图片和首页展示素材
- 首页轮播、推荐位和专题内容
- 活动通知
- 场次、票档、价格和票数
- 购票规则、入场规则和退款规则
- 图文详情模块、阵容、场馆和交通信息
- 草稿编辑、预览、发布、撤回和重新发布
- 活动上下架和公开状态
- 订单、售后和后续运营数据

工作台和购票平台不是两个互不相关的系统。工作台是内容生产端，购票平台是已发布内容的公开消费端。

## 3. 产品事实和设计原则

### 3.1 后台是公开内容的唯一来源

首页轮播图、活动卡片、推荐位、活动名称、封面、活动介绍、通知、场次、票档、价格、库存和购票须知都由后台管理。

购票端不应通过前端代码临时写死这些内容。开发环境可以有初始化数据，但初始化数据也应经过正式的数据模型和发布链路。

### 3.2 草稿和发布快照分离

主办方编辑草稿，用户读取发布快照。编辑未发布草稿时，不应该改变线上用户看到的内容；发布时生成稳定快照；后续才能支持版本记录、撤回和回滚。

### 3.3 页面按任务和身份组织

不能把功能从页面顶部一路堆到底部。购票端围绕“寻找并完成购票”组织，主办方端围绕“创建、发布和承担活动售票责任”组织。

每个页面都需要清楚表达：当前身份、当前对象、当前任务、下一步动作、当前状态和异常兜底。

### 3.4 活动类型决定内容结构

不同活动不应共用完全相同的详情模板。当前内容类型包括：

- PERFORMANCE：演唱会、音乐会、话剧等
- SPORTS：体育赛事
- EXHIBITION：展览、博物馆、休闲活动
- FAMILY：儿童、亲子、家庭活动
- GENERAL：通用活动

类型用于决定后台编辑时的字段建议、规则标题、详情模块和购票端展示顺序，而不是为了制造无意义的复杂度。

## 4. 普通用户的完整业务路径

用户从购票平台进入后，典型路径是：

1. 选择城市或使用默认城市
2. 从首页推荐、分类或搜索进入活动列表
3. 使用时间、类目、价格、城市等条件筛选
4. 打开活动详情，先确认时间、场馆、价格区间和购买状态
5. 阅读活动介绍、阵容、交通和观演须知
6. 选择具体场次
7. 选择票档、数量或座位
8. 填写实名观演人
9. 查看价格明细、优惠、退票规则和支付时限
10. 提交订单并完成支付
11. 在订单中心查看待付款、已付款、已出票、已观演或已退款状态
12. 在电子票页面查看票码、座位和入场信息

这个链路必须比单纯的“查询活动然后点购买”更完整，但每个信息都应出现在用户需要它的上下文中，而不是全部塞到一个页面里。

## 5. 主办方的完整业务路径

主办方进入工作台后，典型路径是：

1. 查看活动列表和当前状态
2. 创建活动并确定类目、城市、活动类型和基础定位
3. 上传封面、详情图片和需要出现在首页的素材
4. 配置场次、场馆、开售时间、票档、价格和库存
5. 编写购票须知、入场须知、退款规则和限制条件
6. 按活动类型填写详情模块
7. 发布活动通知和必要的开票提醒内容
8. 在发布前预览购票端的首页卡片、活动详情和购买入口
9. 校验内容完整性、场次时间、库存和规则冲突
10. 发布活动，使内容生成公开快照
11. 通过工作台继续修改草稿，重新发布新的快照
12. 活动售票期间查看订单、售后和活动状态

主办方不能只负责填写活动名称和价格。后台需要让其对公开内容、销售条件和用户预期承担责任。

## 6. Stage 58 已完成的实现

最新提交 f20cfb0 已完成类型化活动详情发布能力。

### 6.1 五步发布流程

当前发布流程为：

1. 商品定位
2. 场次售票
3. 购票与入场规则
4. 详情内容
5. 预览发布

新增模型：

- EventRule
- EventRuleDraft
- EventDetailSection
- EventDetailSectionDraft

活动、类目和主办方发布对象也已支持内容类型和详情规则关联。

### 6.3 新增数据库结构

H2 和 MySQL 结构均已同步，主要涉及：

- event_rule_catalog
- event_rule_publication
- event_detail_section_catalog
- event_detail_section_publication

这些表分别承担后台编辑数据和公开发布快照。

### 6.4 后台变化

已有活动增加“详情与规则”页签，可以继续维护：

- 活动详情模块
- 购票须知
- 入场须知
- 退款规则
- 其他活动规则

首次保存售票配置时，空规则模板不会再造成后端校验失败。

### 6.5 购票端变化

活动详情页会根据活动类型显示不同的介绍和须知标题。

公开端只读取已发布的活动、图片、规则和详情模块，不直接读取后台草稿。

## 8. 已知边界

当前实现已经形成了活动内容发布骨架，但还没有达到大麦或 12306 的完整生产能力。

尚未完整实现的部分包括：

- 真实支付渠道接入
- 真实座位图和实时选座
- 完整库存预占、释放和高峰排队
- Elasticsearch 搜索
- Redis Lua 库存扣减
- RocketMQ 延迟取消和削峰
- 风控、验证码和防黄牛
- 会员、优惠券、拼团和优先购
- 首页轮播和推荐位的完整后台配置
- 发布审核、版本回滚和权限角色
- 验票入场
- 压力测试和工程证据展示

这些能力不能通过静态按钮或示例数据伪装完成。后续实现应优先建立真实业务闭环。

## 9. 后续产品重点

后续开发的第一优先级是完成内容治理闭环：

- 后台上传图片，购票端展示图片
- 后台创建活动，购票端出现活动
- 后台发布通知，购票端可见通知
- 后台配置分类和推荐位，首页按配置展示
- 后台撤回活动，购票端停止公开购买
- 后台修改草稿，线上旧版本保持稳定
- 发布前可以预览完整购票页面

第二优先级是补齐购票主链路：活动列表、搜索筛选、场次、票档、实名观演人、订单确认、电子票和退款。

第三优先级才是高并发基础设施、验票和工程证据。

## 10. 质量和协作约束

每个阶段都需要具备：

- 明确的产品目标
- 明确的代码范围
- 明确的数据边界
- 可执行的用户验收路径
- 自动化测试
- Git 提交记录
- GitHub 推送结果

前端界面要避免功能堆砌、长页面和无上下文操作。任何按钮都必须有真实状态和对应后端行为，不能只做视觉占位。

任何新建或修改的公开内容，都必须考虑后台是否可视化管理、是否可预览、是否可发布、是否可撤回，以及异常状态下谁负责兜底。
