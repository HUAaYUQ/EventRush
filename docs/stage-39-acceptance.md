# 第 39 阶段验收：压测结果记录区

## 本阶段目标

本阶段在前端工作台中加入压测结果记录区，把抢票压测里的关键数据放到页面上展示。

这一阶段要让你明确看到：

- 压测不能只说“我测过”，要记录具体指标。
- 抢票压测首先要证明没有超卖。
- QPS、平均耗时、P95、P99 是性能表达的基础指标。
- 成功数、失败数、系统异常数是业务正确性表达的基础指标。
- 页面能根据成功数和库存自动判断是否超卖。

## 已完成能力

### 1. 指标记录

页面支持记录：

| 字段 | 含义 |
| --- | --- |
| 模式 | 例如默认 H2/本地基线、Redis Lua 库存 |
| Users | 本轮压测用户数 |
| 票档库存 | 被压测票档的库存 |
| 成功数 | 抢票成功订单数 |
| 失败数 | 抢票失败请求数 |
| QPS | 每秒处理请求数 |
| 平均耗时 ms | 平均响应耗时 |
| P95 ms | 95% 请求小于等于该耗时 |
| P99 ms | 99% 请求小于等于该耗时 |
| 系统异常数 | 500 或非预期系统错误数量 |

### 2. 自动判断是否超卖

判断规则：

```text
成功数 > 票档库存 = 超卖
成功数 <= 票档库存 = 未超卖
```

抢票压测里，未超卖比单纯 QPS 更重要。因为票务系统的第一底线是业务正确。

### 3. 自动给出结论

当前结论规则：

```text
未超卖 且 系统异常数为 0 = 通过
发生超卖 或 系统异常数大于 0 = 需复查
```

这是第一版最小规则。后续可以继续增加阈值，比如 P95 必须低于某个目标值。

## 验收方式

### 前端构建

在 `frontend` 目录执行：

```powershell
npm.cmd run build
```

预期结果：

- 构建成功。

### 后端测试

在项目根目录执行：

```powershell
mvn test
```

预期结果：

- 测试全部通过。

### 页面手动验收

启动后端：

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=18086"
```

启动前端：

```powershell
cd frontend
npm.cmd run dev
```

访问：

```text
http://localhost:5173
```

操作步骤：

1. 找到“压测结果记录”区域。
2. 输入模式，例如 `默认 H2/本地基线`。
3. 输入 Users、票档库存、成功数、失败数、QPS、平均耗时、P95、P99、系统异常数。
4. 当成功数小于等于库存，并且系统异常数为 0 时，确认结论为“通过”。
5. 把成功数改成大于库存，确认“是否超卖”为“是”，结论变为“需复查”。
6. 把系统异常数改成大于 0，确认结论变为“需复查”。

当前先把指标字段和判断规则固定下来，后续再做可视化会更稳。

## 你需要学会的点

- 压测不是只看 QPS。
- 抢票系统压测首先要看是否超卖。
- P95、P99 比平均耗时更能说明尾部延迟。
- 成功数不能超过库存，这是业务正确性的底线。
- 系统异常数要单独记录，不能混在普通业务失败里。

## 面试表达

可以这样说：

> 我在项目里加入了压测结果记录区，记录 Users、库存、成功数、失败数、QPS、平均耗时、P95、P99 和系统异常数。页面会根据成功数和库存判断是否超卖，并根据是否超卖、是否有系统异常给出结论。这样压测结果不是口头描述，而是能作为项目展示证据。
