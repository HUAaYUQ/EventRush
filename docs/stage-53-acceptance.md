# Stage 53 验收：主办方活动发布中心

## 目标

为活动主办方建立独立入口，围绕“活动列表 → 发布流程 → 单活动管理”完成活动发布和维护，不把购票、验票、工程证据或压力测试混进同一套导航。

## 做了什么

- 新增 `/organizer/events` 活动列表：按草稿、已发布和票量查看主办方自己的活动。
- 新增 `/organizer/events/new` 四步发布流程：基本信息、场次时间、票档库存、发布检查。
- 新增 `/organizer/events/:eventId` 单活动管理：概览、场次与票档、通知三个工作区。
- 增加草稿本地恢复、封面预览、发布前检查和移动端抽屉导航。
- 后端新增 H2 活动目录、场次、票档、通知持久化模型，并用 `X-Organizer-Key` 保护主办方接口。
- 公开购票目录只展示 `PUBLISHED` 活动，主办方草稿不会提前暴露给购票用户。

## 你要学会什么

- 主办方和购票用户是两种不同的日常任务，应该通过入口和工作流隔离，而不是靠一页里的标签切换。
- 发布流程应按决策顺序拆分，每一步只处理一类信息，最后集中检查，降低“表单字段堆砌”的认知负担。
- 草稿、发布和公开可见是明确的状态边界；权限校验和公开目录过滤要在后端落地，不能只依赖前端隐藏。
- 活动是主对象，场次、票档和通知是围绕活动展开的管理动作，后续扩展报名规则或退款政策也应沿着这个对象组织。

## 怎么验收

1. 启动后端和前端，打开 `http://localhost:5173/organizer/events`。
2. 使用默认主办方密钥 `eventrush-organizer-key`，确认能看到活动列表；输入错误密钥应显示连接失败态。
3. 进入“发布新活动”，依次填写活动信息、场次、票档，确认每一步都能保存并可返回修改。
4. 在发布检查中确认四项均通过后发布，回到单活动管理页，检查概览、场次与票档、通知三个标签。
5. 返回购票端活动目录，确认已发布活动可见；另创建一个草稿，确认草稿不可见。
6. 在 320px、375px、414px、768px 和桌面宽度检查：导航抽屉、发布步骤、表格字段和操作按钮没有横向溢出。

## 本阶段边界

验票入口、运营排查、工程证据和压力测试继续保留兼容地址，但不进入主办方中心的正式导航；真实支付网关、座位图和多角色登录留待后续阶段。
