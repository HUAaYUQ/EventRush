# EventRush 前端成果接收清单

这份文档是你接收前端工作台成果时使用的操作脚本。目标不是让你只点按钮，而是让你知道每一步在验证什么业务能力、该记录什么结果、面试时怎么复述。

## 接收前准备

### 1. 启动后端

在项目根目录执行：

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=18086"
```

预期结果：

- 后端服务运行在 `18086` 端口。
- 本地默认使用 H2。
- 不需要先启动 Redis、RocketMQ。

### 2. 启动前端

在前端目录执行：

```powershell
cd frontend
npm.cmd run dev
```

访问：

```text
http://localhost:5173
```

预期结果：

- 页面能打开。
- 活动列表能自动加载。
- 顶部统计能看到活动、场次、票档和剩余库存。

## 接收主线

### 第一步：活动与票档

操作：

1. 打开页面。
2. 查看“活动与票档”区域。
3. 选择一个有库存的票档。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 活动列表 | 能显示活动名称、地点、状态 |
| 场次 | 能显示 `sessionId` 和时间 |
| 票档 | 能显示票档名称和剩余库存 |
| 选择结果 | 同步抢票区能带出 `sessionId`、`ticketCategoryId` |

你要理解：

> 抢票不是凭空发生的，它必须绑定具体场次和票档。前端把 `sessionId`、`ticketCategoryId` 传给后端，后端才知道扣哪一类库存。

### 第二步：同步抢票

操作：

1. 输入一个新的 `userId`。
2. 点击“同步抢票”。

你要确认：

| 项目 | 期望 |
| --- | --- |
| `orderId` | 页面出现订单 ID |
| 订单状态 | `PENDING_PAYMENT` |
| 支付截止 | 页面出现过期时间 |
| traceId | 页面展示抢票接口 traceId |

你要理解：

> 抢票成功只是拿到购买资格，所以订单是待支付状态。此时还没有电子票，支付后才会出票。

### 第三步：支付出票

操作：

1. 在已有订单基础上点击“支付并出票”。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 订单状态 | 刷新为 `PAID` |
| `ticketCode` | 页面出现电子票票码 |
| 票状态 | `VALID` |
| traceId | 页面展示支付接口 traceId |

你要理解：

> 订单负责交易状态，电子票负责入场凭证。支付成功后订单变成 `PAID`，系统生成一张 `VALID` 电子票。

### 第四步：电子票查询与验票

操作：

1. 点击“查询电子票”。
2. 确认票状态为 `VALID`。
3. 保留默认验票员 ID，点击“验票入场”。
4. 再点一次“验票入场”。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 查询电子票 | 能查到同一个 `ticketCode` |
| 验票前状态 | `VALID` |
| 验票后状态 | `VERIFIED` |
| 重复验票 | 后端拒绝，页面展示错误 |

你要理解：

> 验票必须由后端检查票状态。只有 `VALID` 的票能变成 `VERIFIED`，重复验票会被拒绝，防止同一张票重复入场。

### 第五步：管理端排查

操作：

1. 确认 `X-Admin-Key` 是 `eventrush-admin-key`。
2. 点击“按用户查订单”。
3. 点击“按订单查票”。
4. 点击“按票码查票”。
5. 把 `X-Admin-Key` 改成错误值，再查一次。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 按用户查订单 | 能查到当前用户订单 |
| 按订单查票 | 返回的 `ticketCode` 和支付结果一致 |
| 按票码查票 | 票状态和验票结果一致 |
| 错误密钥 | 返回鉴权失败 |

你要理解：

> 管理端排查不是另一个业务流程，而是用后台视角证明用户侧看到的订单和电子票真实存在，并且状态一致。

### 第六步：压测结果记录

操作：

1. 找到“压测结果记录”区域。
2. 输入一组压测数据。
3. 修改成功数和系统异常数，观察结论变化。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 成功数小于等于库存 | 是否超卖为“否” |
| 成功数大于库存 | 是否超卖为“是” |
| 系统异常数为 0 | 可作为通过条件之一 |
| 系统异常数大于 0 | 结论变为“需复查” |

你要理解：

> 抢票压测首先看有没有超卖，再看 QPS、P95、P99。成功数超过库存，就算 QPS 很高也不是有效结果。

### 第七步：压测对比展示

操作：

1. 找到“压测对比展示”区域。
2. 保持默认方案和 Redis Lua 方案使用同一组 Users 和库存。
3. 填写两组 QPS、P95、P99。
4. 调整 Redis Lua 的 QPS 和 P95，观察整体结论。

你要确认：

| 项目 | 期望 |
| --- | --- |
| 两组都未超卖 | 单行结论为“通过” |
| 任一组超卖 | 本轮对比不能作为有效优化结论 |
| Redis Lua QPS 更高且 P95 没变差 | 页面提示可作为优化候选证据 |
| 参数不一致 | 不应该直接拿来比较 |

你要理解：

> 优化对比必须同参数、同口径。Redis Lua 的价值要通过“默认方案 vs Redis Lua 方案”的数据体现，而不是只说用了 Redis。

## 一次完整演示脚本

你可以按下面顺序讲：

1. 这是 EventRush 的票务工作台，第一屏直接展示活动、场次、票档和库存。
2. 我选择一个票档，用一个用户发起同步抢票，后端创建 `PENDING_PAYMENT` 订单。
3. 我支付这个订单，订单变成 `PAID`，系统生成 `VALID` 电子票。
4. 我通过票码查询电子票，再进行验票，电子票从 `VALID` 变成 `VERIFIED`。
5. 我重复验票一次，后端拒绝，说明验票有幂等和防重复入场控制。
6. 我用管理端密钥反查用户订单、订单对应票、票码详情，证明用户侧结果和后台数据一致。
7. 最后看压测记录和压测对比，不只看 QPS，也看是否超卖、P95、P99 和系统异常。

## 面试复述版本

> 前端工作台不是普通展示页，而是项目验收入口。它能跑通用户抢票、支付出票、电子票查询和验票；也能通过管理端接口反查订单和票码，证明数据真实落库；最后还能记录压测结果和默认方案、Redis Lua 方案的同口径对比。这样演示时可以从业务链路、后台排查、性能证据三个层面说明项目不是只写了接口，而是能被验证、能被复盘。
