# 第 30 阶段验收：手动验收结果记录模板

## 本阶段交付

- 新增手动验收结果记录模板：`docs/manual-acceptance-record-template.md`。
- 模板覆盖启动记录、活动查询、抢票、支付、查单、查票、验票和管理端查询。
- 模板支持记录 `userId`、`orderId`、`ticketCode`、`traceId` 和状态流转。
- 模板包含异常记录和最终结论，方便复盘。
- 在 `README.md` 和 `docs/learning-map.md` 中补充入口。

## 为什么要做这一阶段

第 29 阶段已经跑通完整业务链路。第 30 阶段要把“跑通过”变成“有证据可复盘”。

这一阶段要解决的问题是：

- 手动验收不能只停留在口头说通过。
- 每次验收都要记录输入、输出、关键 ID 和状态。
- 出问题时要能记录现象、原因判断和处理方式。
- 后续做 UI 时，也可以沿用这份模板验收前端调用链路。

## 手动验收

打开：

```text
docs/manual-acceptance-record-template.md
```

检查以下内容：

- 是否能记录启动端口和环境配置。
- 是否能记录活动查询结果。
- 是否能记录抢票的 `userId`、`orderId` 和订单状态。
- 是否能记录支付返回的 `ticketCode`。
- 是否能记录订单和电子票状态流转。
- 是否能记录管理端查询结果。
- 是否有异常记录和最终结论。

## 你需要学会的点

- 验收记录的价值是让项目结果可复盘、可展示、可交接。
- `orderId` 和 `ticketCode` 是完整链路里最关键的两个变量。
- `traceId` 是排查接口问题时的重要证据。
- 状态流转比“接口返回 200”更重要。
- 异常记录不是失败记录，而是说明你能定位和处理问题。

## 面试表达

可以这样说：

> 我给项目补了手动验收结果记录模板。每次跑完整链路时，我会记录启动环境、请求参数、orderId、ticketCode、traceId、订单状态、电子票状态和管理端查询结果。这样项目不是只说“我测过”，而是能拿出状态流转和验收结论作为证据。
