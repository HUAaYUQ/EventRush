# 第 31 阶段验收：产品输出蓝图

## 本阶段目标

本阶段不急着安装 Skill，也不急着写前端页面，而是先确定 EventRush 最终要输出成什么产品形态。

原因是：前端、压测可视化、面试展示和后续优化都应该服务于同一个核心目标。如果目标不清楚，后面很容易变成“做了很多功能，但讲不出主线”。

## 本阶段交付

新增文档：

```text
docs/product-output-blueprint.md
```

这份文档明确了：

- EventRush 的产品定位：高并发票务操作工作台。
- 是否需要区分身份：普通用户、验票人员、管理人员。
- 后续 UI 应该展示哪些模块。
- 单链路验收、正确性压测、性能对比三层数据证据。
- 面试展示应该如何组织表达。
- 后续优化路线和暂不优先事项。

## 核心决策

### 1. 不做普通票务商城

EventRush 的价值不是“像大麦一样卖票”，而是证明你理解高并发票务后端中的核心问题。

所以页面不能只展示活动卡片和购买按钮，还要展示：

- 订单状态。
- 电子票状态。
- 错误码和 traceId。
- 管理端查询。
- 压测结果。
- 后续优化对比。

### 2. 需要区分身份，但先不做复杂登录

产品上区分三类身份：

| 身份 | 作用 |
| --- | --- |
| 普通用户 | 抢票、支付、查看电子票 |
| 验票人员 | 输入票码并核验入场 |
| 管理人员 | 查询订单、票码和用户记录，排查问题 |

当前阶段不引入完整登录注册，因为这不是项目核心。管理端继续使用 `X-Admin-Key`，后续需要时再升级。

### 3. 数据证据必须分层

后续展示不能只说“我做了压测”，而要能拿出证据。

第一层：单链路验收数据，证明业务闭环能跑通。

第二层：正确性压测数据，证明高并发下没有超卖、没有重复成功订单。

第三层：性能对比数据，证明 Redis Lua、RocketMQ、限流等优化带来的变化。

通过。

## 你需要学会的点

- 严谨的项目推进要先定目标，再定页面，再写代码。
- 身份划分来自业务流程，不是为了显得功能多。
- 面试项目必须有证据链：手动验收、自动化测试、压测报告、优化对比。
- 本地学习压测和生产性能结论要区分开，不能混着讲。
- 前端 UI 应该帮助别人看懂你的后端能力，而不是盖住它。
