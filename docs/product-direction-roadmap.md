# EventRush 方向总纲

这份文档不是功能清单，也不是演示说明书。它的作用只有一个：告诉我们 EventRush 接下来应该往哪里走，先解决谁的问题，哪些能力必须做，哪些能力先放后面。

## 先说结论

现在的 EventRush 还不是一个完整产品，它更像是一个把“业务演示、工程证据、压测结果、后台排查”混在一起的工作台。

这会带来三个问题：

1. 默认首屏没有明确用户目标。
2. 不同角色的需求被放在同一层级里。
3. 工程证明挤占了真实产品路径。

所以下一步不是继续堆页面，而是把产品边界拆开。

## 我们到底要做什么

EventRush 应该变成一个面向真实票务场景的产品集合，而不是单页展示台。它至少要同时服务四类人。

### 1. 普通用户

他们关心的是：

- 看活动和场次。
- 看票档和库存。
- 下单和支付。
- 看自己的电子票。
- 退票或取消订单。
- 接收通知提醒。

### 2. 活动主办方

他们关心的是：

- 发布场次。
- 维护票档和库存。
- 看最近活跃的活动。
- 看售卖状态和异常情况。
- 需要时做下架、取消、补充说明。

### 3. 工作人员

他们关心的是：

- 验票。
- 判断是否重复入场。
- 看票码状态。
- 处理现场核验失败。

### 4. 工程与运营

他们关心的是：

- 查请求。
- 看 traceId。
- 排查失败。
- 做压力测试。
- 看系统是否稳定、是否超卖、是否有性能退化。

## 参考对标

借鉴 [12306](https://github.com/nageoffer/12306/blob/main/README.md) 的重点，不是界面样式，而是角色边界和流程边界。

它至少说明了一件事：

- 用户先完成查票、下单、支付、出票。
- 验票是独立流程。
- 后台排查是另一条线。

这正是我们现在最缺的。

## 产品边界

EventRush 以后应该分成四个入口，而不是一个默认大杂烩。

### A. 票务前台

这是给普通用户看的主产品。

必须包含：

- 活动列表。
- 场次列表。
- 票档和库存。
- 下单。
- 支付。
- 电子票查看。
- 退票或取消的入口。
- 通知提醒入口。

### B. 主办方控制台

这是给活动主办方看的。

必须包含：

- 发布活动。
- 新增或修改场次。
- 管理票档。
- 查看最近活跃活动。
- 看到售卖和异常状态。

### C. 工作人员验票台

这是给现场工作人员看的。

必须包含：

- 票码输入或扫码。
- 票状态。
- 核验结果。
- 重复验票提示。
- 失败原因。

### D. 工程证据台

这是给开发、测试、面试展示看的。

必须包含：

- 最近请求记录。
- traceId。
- 压测结果。
- 超卖判断。
- 性能对比。
- 管理查询。

## 真实场景必须考虑什么

如果不考虑下面这些，项目就还是“自我感动”。

- 库存不足。
- 用户重复点击。
- 支付失败后重试。
- 订单超时未支付。
- 同一票码重复验票。
- 活动取消或下架。
- 网络抖动导致的重复请求。
- 用户退票或取消订单。
- 短信、站内信、邮件通知延迟。
- 高并发下的库存正确性。

## 现在必须优先做的事情

### P0

- 把票务前台做成真正可用的主入口。
- 把验票做成独立流程。
- 把工程证据收进独立入口。
- 把主办方和工作人员从普通用户路径里拆出来。
- 把“退票、通知、异常状态”纳入产品边界。

### P1

- 主办方控制台。
- 更完整的订单状态流转。
- 退票流程。
- 通知中心。
- 运营排查能力加强。

### P2

- 更细的权限体系。
- 更完整的统计和监控。
- 更强的告警和审计。
- 复杂座位图和选座流程。

## 当前不该做的事

- 不要把压测和请求记录放到默认首屏。
- 不要把工程证据伪装成用户产品。
- 不要让一个页面同时承担四种角色。
- 不要先做炫技式 UI，再补业务边界。
- 不要只盯着“能跑通”，要盯着“真实用户能不能用”。

## 页面结构原则

以后每个入口都要先回答一个问题。

- 用户入口，回答“我怎么购票”。
- 主办方入口，回答“我怎么发活动”。
- 工作人员入口，回答“我怎么验票”。
- 工程入口，回答“我怎么排查和证明稳定性”。

如果一个页面回答了两个以上问题，就要重新拆。

## 验收标准

一个合格的版本，至少要满足下面这些条件：

- 普通用户能完整走完看票、下单、支付、看电子票。
- 工作人员能完成验票和重复验票判断。
- 主办方能看到活动和场次的管理入口。
- 工程侧能快速查到请求、错误和 traceId。
- 压测能证明系统没有超卖。
- 失败场景有明确提示，不是只有成功路径。

## 下一步建议

下一轮不要再从“页面怎么摆”开始，而要从“角色和流程怎么拆”开始。

建议顺序是：

1. 先定义每个角色的首页。
2. 再定义每个角色的关键动作。
3. 再定义失败场景。
4. 再定义数据和状态。
5. 最后才是 UI 细化。

## 一句话总结

EventRush 不是一个只展示接口和压测的项目，它应该是一个真实票务产品加独立工程证据系统。用户路径要像产品，工程证据要像后台，二者不能再混在同一层。
