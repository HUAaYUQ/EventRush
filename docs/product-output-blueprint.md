# EventRush 产品输出蓝图

这份文档用来回答一个更根本的问题：EventRush 最终要交付成什么样，给谁看，用什么证据证明它不是一个只会跑接口的练习项目。

结论先放前面：EventRush 的产品输出不应该是普通票务商城，也不应该是炫技型首页。它应该是一个“高并发票务操作工作台”，重点展示完整业务闭环、后台排查能力、压测证据和后续优化空间。

## 产品定位

EventRush 面向的是活动票务高并发场景，核心问题不是“卖票页面好不好看”，而是：

- 高并发下库存是否会超卖。
- 用户重复点击、重复支付、重复验票时系统是否稳定。
- 订单从待支付到已支付、已取消是否有清晰状态流转。
- RocketMQ、Redis 等中间件能力是否能解释清楚，而不是只为了堆技术栈。
- 出问题后是否能通过 traceId、后台查询和验收记录快速定位。
- 面试展示时是否能拿出真实流程、真实数据和可复盘文档。

因此，前端和展示材料都要围绕“业务正确性 + 工程证据 + 面试表达”展开。

## 用户身份划分

产品上建议至少分成三类身份，但实现上可以先用页面分区和轻量密钥完成，不急着引入完整登录系统。

| 身份 | 核心目标 | 需要看到什么 | 当前项目支撑情况 |
| --- | --- | --- | --- |
| 普通用户 | 抢票、支付、查看电子票 | 活动列表、票档库存、订单状态、票码、验票结果 | 已有用户端接口支撑 |
| 验票人员 | 判断一张票能否入场 | 票码输入、票状态、核验结果、重复验票提示 | 已有验票接口支撑 |
| 管理人员 | 排查订单、用户和票码问题 | 按用户查订单、按订单查票、按票码查票、traceId | 已有管理端接口和 `X-Admin-Key` 支撑 |

当前阶段不建议做复杂账号体系。原因是：这个项目的面试重点是高并发票务链路，不是用户权限系统。管理端先保留 `X-Admin-Key`，后续如果需要再升级成登录、角色、权限。

## 核心页面输出

后续 UI 可以按“工作台”来设计，而不是按营销网站来设计。

| 页面/区域 | 展示内容 | 对应能力 | 面试价值 |
| --- | --- | --- | --- |
| 活动与票档区 | 活动、场次、票档、剩余库存 | 活动查询、库存展示 | 说明业务模型拆分 |
| 抢票操作区 | 用户 ID、抢票按钮、同步/异步模式 | 抢票、异步请求、重复抢票保护 | 说明高并发入口 |
| 订单与支付区 | 订单状态、支付按钮、支付结果 | 订单状态机、支付幂等 | 说明状态流转和幂等 |
| 电子票区 | 票码、票状态、出票时间 | 出票、查票 | 说明订单和电子票职责拆分 |
| 验票区 | 票码输入、核验按钮、核验结果 | 验票、防重复核验 | 说明入场核验边界 |
| 管理查询区 | 用户订单、订单票据、票码详情 | 管理端查询、轻量鉴权 | 说明后台排查能力 |
| 链路排查区 | traceId、错误码、错误信息 | 统一响应、traceId | 说明接口治理 |
| 压测证据区 | 请求数、成功数、失败数、QPS、P95、P99、是否超卖 | 压测脚本、报告模板 | 说明优化有数据支撑 |

第一版 UI 不需要追求复杂动效。它应该让人一打开就能完成一条完整链路：查活动 -> 抢票 -> 支付 -> 查票 -> 验票 -> 管理端排查。

## 数据证据设计

“实打实的数据支撑”建议分三层。

### 第一层：单链路验收数据

用于证明业务闭环能跑通。

必须记录：

- `userId`
- `orderId`
- `ticketCode`
- 抢票前后库存变化
- 订单状态变化：`PENDING_PAYMENT -> PAID`
- 电子票状态变化：`VALID -> VERIFIED`
- 管理端查询结果
- 每一步的 `traceId`

已有支撑文档：

- `docs/end-to-end-manual-acceptance.md`
- `docs/manual-acceptance-record-template.md`
- `docs/stage-29-acceptance.md`

### 第二层：正确性压测数据

用于证明高并发下没有超卖，而不是只看 QPS。

必须记录：

- 压测环境：操作系统、Java 版本、数据库、中间件开关。
- 压测参数：并发数、总请求数、用户 ID 范围、票档库存。
- 结果指标：成功数、失败数、剩余库存、订单数。
- 正确性结论：成功订单数是否小于等于初始库存，是否出现重复用户订单。

核心判断：

```text
成功订单数 + 剩余库存 = 初始库存
同一用户同一票档最多只有一条成功订单
```

已有支撑文档：

- `docs/pressure-test-guide.md`
- `docs/pressure-test-report-template.md`
- `docs/redis-lua-pressure-switch.md`

### 第三层：性能对比数据

用于展示后续优化，而不是现在强行追求漂亮数字。

建议对比：

- H2/数据库基础方案。
- Redis Lua 库存扣减方案。
- 同步抢票和 RocketMQ 异步抢票方案。
- 开启限流前后，失败是否更可控。

建议展示指标：

- QPS
- 平均响应耗时
- P95
- P99
- 成功率
- 业务失败原因分布
- 是否超卖

这里要特别注意：本地 Windows + H2 的压测只能作为学习基线，不应该包装成生产性能结论。面试里更严谨的说法是“我用同一组参数对比不同方案，观察正确性和延迟变化”。

## 面试展示结构

面试时建议按下面顺序讲，而不是从技术栈开始背。

1. 业务问题：抢票最怕超卖、重复请求、状态错乱。
2. 业务闭环：活动查询、抢票、支付、出票、验票、后台排查。
3. 正确性设计：库存扣减、重复抢票保护、支付幂等、验票幂等。
4. 异步能力：RocketMQ 异步抢票、订单超时取消、兜底扫描。
5. 接口治理：统一响应、traceId、管理端鉴权。
6. 数据证据：手动验收记录、压测报告、优化对比。
7. 后续优化：Redis Lua、限流、异步削峰、监控可视化、权限系统。

一句话版本：

> EventRush 不是只做了几个接口，而是围绕高并发票务场景，把业务闭环、库存正确性、幂等、异步处理、后台排查和压测证据串成了一套可演示、可复盘、可面试表达的项目。

## 后续优化路线

后续优化必须围绕证据推进，不建议为了堆技术点随意加功能。

| 优先级 | 优化方向 | 为什么做 | 验收证据 |
| --- | --- | --- | --- |
| P0 | 前端工作台 | 让业务链路可视化，降低演示成本 | 能完整跑通用户、验票、管理三条链路 |
| P0 | 压测结果可视化 | 让性能和正确性有数据支撑 | 图表展示成功数、失败数、QPS、P95、P99、是否超卖 |
| P1 | Redis Lua 对比压测 | 展示高并发库存方案差异 | 同参数对比基础方案和 Redis Lua 方案 |
| P1 | RocketMQ 异步演示 | 展示削峰和异步结果查询 | requestId、处理中、成功、失败状态可见 |
| P1 | 错误场景展示 | 证明边界处理完整 | 重复抢票、库存不足、重复支付、重复验票都有明确提示 |
| P2 | 管理端权限升级 | 从轻量密钥升级到角色权限 | 登录、角色、接口保护测试 |
| P2 | 监控指标面板 | 更接近生产排查方式 | 请求量、错误率、耗时分布、traceId 检索 |

## 当前阶段不做什么

为了保证项目根基严谨，下面这些暂时不优先做：

- 不先做营销型首页。
- 不先做复杂登录注册。
- 不先做多租户、优惠券、座位图等票务扩展。
- 不为了 UI 好看而隐藏业务状态。
- 不把本地压测数据包装成生产性能结论。

这些不是永远不做，而是等核心链路、证据和展示目标稳定后再做。

## 你需要学会的点

- 产品输出不是“功能列表”，而是“这个项目最终要证明什么”。
- 用户端、验票端、管理端不是为了页面多，而是对应真实业务角色。
- 压测不能只看 QPS，必须先看是否超卖、是否重复订单。
- UI 不是装饰，它应该帮助展示业务状态、错误边界和排查能力。
- 面试展示要用“问题 -> 方案 -> 证据 -> 后续优化”的结构。
