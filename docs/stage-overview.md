# EventRush 阶段总览

这份文档用来把第 1 到第 24 阶段串成一张复习表。你可以把它当成项目的“成果接收清单”：每一阶段做了什么、解决了什么问题、应该掌握什么点，都可以从这里快速回看。

## 怎么使用这份总览

建议你按三层来复习：

1. 先看“业务链路”，确认自己能讲清楚用户从抢票到验票发生了什么。
2. 再看“高并发能力”，确认自己能讲清楚防超卖、幂等、MQ、Redis Lua。
3. 最后看“工程表达”，确认自己能用 README、API 文档、压测报告把项目讲给别人听。

## 按主题复习

### 业务主线

对应阶段：1、2、12、17、19。

你要能讲清楚：

- 活动、场次、票档、订单、电子票分别是什么。
- 为什么抢票成功后先生成待支付订单。
- 为什么支付成功后才生成电子票。
- 为什么管理端需要查询订单和票码。

一句话表达：

> EventRush 先完成票务业务闭环，再逐步增强库存、幂等、异步、缓存和排查能力，保证项目不是散点功能，而是一条完整业务链路。

### 防超卖和幂等

对应阶段：4、5、6、10、12。

你要能讲清楚：

- 抢票最核心的问题是库存不能超卖。
- 同一用户同一票档不能重复抢。
- 支付接口重复调用不能重复出票。
- MQ 消息重复消费不能重复处理业务。
- 数据库唯一约束是最后一道兜底。

一句话表达：

> 我把防超卖、防重复抢票、支付幂等和消费幂等拆在不同层处理，代码层先判断状态，数据库层再用唯一约束兜底。

### Redis 和 Lua

对应阶段：3、5、7、22、24。

你要能讲清楚：

- Redis 在项目里有缓存、库存、限流三个角色。
- 本地默认不依赖 Redis，相关能力都通过开关启用。
- Lua 脚本把库存检查、重复用户检查、扣库存合成一次原子执行。
- 压测 Redis Lua 方案时要和默认方案使用相同参数。

一句话表达：

> Redis Lua 方案的价值不是“用了 Redis”，而是把抢票里的多步判断和扣减放进一次原子执行，降低并发竞争带来的风险。

### RocketMQ 和异步

对应阶段：8、9、10、11、21。

你要能讲清楚：

- 异步抢票为什么先返回 requestId。
- RocketMQ 在项目里负责抢票消息和订单超时消息。
- 延时消息到期后不能直接取消订单，必须先查状态。
- MQ 不可用时为什么还需要兜底扫描。

一句话表达：

> MQ 用来削峰和解耦，但不能替代业务正确性判断，所以消费者处理消息时仍然要查状态、做幂等、保留兜底。

### 接口治理和排查

对应阶段：13、14、15、16、18、19。

你要能讲清楚：

- 统一响应让前端和调用方更容易处理结果。
- traceId 让响应、日志和问题排查关联起来。
- 管理端接口需要鉴权，密钥要能通过环境变量配置。
- API 文档要写通用规则、错误码和完整链路。

一句话表达：

> 接口治理不是装饰，它解决的是联调一致性、错误处理一致性和线上排查效率。

### 压测和项目表达

对应阶段：20、22、23、24。

你要能讲清楚：

- 抢票压测先验证不超卖，再看 QPS、P95、P99。
- 本地 H2/Windows/PowerShell 压测只能作为学习基线。
- 压测报告要记录环境、参数、输出和结论。
- 面试里要用“问题 -> 方案 -> 验证 -> 风险”来讲项目。

一句话表达：

> 压测不是为了报一个漂亮数字，而是证明在给定条件下系统没有超卖，并且能用指标描述优化前后的变化。

## 最短讲项目版本

如果只有 1 分钟，可以这样讲：

> EventRush 是一个高并发活动票务后端项目。我先实现活动查询、抢票、支付出票、验票和后台查询的完整链路，再围绕抢票场景补充防超卖、防重复抢票、支付幂等、消息消费幂等、订单超时取消、Redis Lua 库存扣减、RocketMQ 异步处理、统一响应、traceId 和管理端鉴权。项目默认用 H2 就能本地运行，Redis 和 RocketMQ 都通过配置开关启用；同时补了 API 文档、阶段验收文档、压测指南和压测报告模板，方便验证和面试表达。
