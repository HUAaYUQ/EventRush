# Stage 55：主办方订单与售后概览验收

## 这一阶段做了什么

主办方活动详情新增“订单与售后”视图。它围绕单个活动查看订单状态、购票用户、场次、票档、数量、金额、退票数量和出票数量。

本阶段只读展示运营事实，不在主办方端直接执行退款。退款仍由购票用户在个人订单中发起，主办方通过订单状态和退票数量跟进售后，避免权限边界混乱。

后端新增接口：

```text
GET /api/organizer/events/{eventId}/orders
```

接口继续使用 `X-Organizer-Key` 鉴权，并返回订单摘要而不是购票人的敏感证件信息。

## 你应该学会什么

- 为什么主办方需要订单视图，但不应该直接拥有用户退款操作权限。
- 如何把订单状态、退票数量和出票数量放在同一个活动上下文中核对。
- 为什么订单列表需要同时支持加载中、空数据和接口错误状态。
- 如何用一条“发布活动 → 创建订单 → 主办方查询订单”的接口链路验证跨角色数据一致性。

## 怎么验收

### 自动化验收

在项目根目录执行：

```powershell
mvn -q "-Dtest=OrganizerApiTest" test
mvn test
```

在前端目录执行：

```powershell
npm.cmd run build
```

### 浏览器验收

1. 打开 `http://localhost:5173/organizer/events`。
2. 进入一个活动，点击“订单与售后”。
3. 确认能看到订单总数、已付款订单、发生退票、已出票四个摘要。
4. 确认订单行展示订单号、状态、用户 ID、票档、场次、数量、金额、退票和出票数量。
5. 刷新页面，确认订单仍然从接口读取，而不是依赖前端临时数据。
6. 没有订单时，确认页面给出“暂时没有订单”的下一步提示；接口失败时，确认页面给出错误信息。
7. 在手机宽度下确认订单行变为单列，金额和数量不会互相遮挡。

## 面试表达

> 主办方工作台不是把购票端所有能力复制一遍，而是围绕“活动运营”提供只读的订单与售后概览。退款仍由用户发起，主办方查看状态和出票结果，这样既能支持运营排查，也保持了角色权限边界。
