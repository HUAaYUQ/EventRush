# 第 40 阶段验收：压测对比展示

## 本阶段目标

本阶段在前端工作台中加入压测对比展示，把默认方案和 Redis Lua 库存方案放在同一组指标下比较。

这一阶段要让你明确看到：

- 优化对比必须使用同一组压测参数。
- 两组方案都必须先确认没有超卖。
- QPS、P95、P99 要放在同一张表里比较。
- 如果任一方案发生超卖或系统异常，本轮对比不能作为有效优化结论。
- Redis Lua 是否更好，要看同口径数据，而不是只看“用了 Redis”。

## 已完成能力

### 1. 两组方案对比

页面默认提供两行数据：

| 模式 | 含义 |
| --- | --- |
| 默认 H2/本地基线 | 默认本地方案，不启用 Redis 库存 |
| Redis Lua 库存 | 开启 `eventrush.stock.redis-enabled=true` 后的 Redis Lua 库存方案 |

每一行支持记录：

- Users
- 库存
- success
- failed
- QPS
- P95
- P99
- 系统异常数

### 2. 单行结论

每一行会自动判断：

```text
success <= 库存 且 系统异常数 = 0 => 通过
success > 库存 或 系统异常数 > 0 => 需复查
```

### 3. 整体对比结论

当前整体结论规则：

```text
任一方案需复查 => 本轮对比不能作为有效优化结论
两组都通过，且 Redis Lua QPS 更高、P95 没有变差 => Redis Lua 可作为优化候选证据
两组都通过，但性能优势不明显 => 需要更多轮压测判断
```

这是第一版最小规则，后续可以继续加入平均耗时、P99、成功率等综合评分。

## 验收方式

### 前端构建

在 `frontend` 目录执行：

```powershell
npm.cmd run build
```

预期结果：

- 构建成功。

### 后端测试

在项目根目录执行：

```powershell
mvn test
```

预期结果：

- 测试全部通过。

### 页面手动验收

启动后端：

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=18086"
```

启动前端：

```powershell
cd frontend
npm.cmd run dev
```

访问：

```text
http://localhost:5173
```

操作步骤：

1. 找到“压测对比展示”区域。
2. 确认有默认方案和 Redis Lua 方案两行。
3. 两行都输入相同 Users 和库存。
4. 确认 success 小于等于库存、系统异常数为 0 时，单行结论为“通过”。
5. 把任意一行 success 改成大于库存，确认该行变为“需复查”。
6. 把任意一行系统异常数改成大于 0，确认该行变为“需复查”。
7. 把 Redis Lua 的 QPS 改成高于默认方案，且 P95 小于等于默认方案，确认整体结论显示 Redis Lua 可作为优化候选证据。

## 本阶段边界

本阶段暂不做：

- 自动运行压测脚本。
- 自动读取压测报告。
- ECharts 图表。
- 多轮历史记录。

当前先固定优化对比的表达结构，避免在数据口径没稳定前过早做图表。

## 你需要学会的点

- 性能优化要做同参数对比。
- 没有业务正确性，QPS 再高也不能算有效优化。
- P95 没有变差比平均耗时更适合说明尾部稳定性。
- Redis Lua 的价值是原子库存扣减和防重复抢票，不是“用了 Redis 就一定更快”。
- 面试里讲优化，要用“默认方案 vs 优化方案”的数据说话。

## 面试表达

可以这样说：

> 我在前端工作台里加入了压测对比展示，把默认方案和 Redis Lua 库存方案放在同一组 Users、库存和票档参数下比较。每组数据都会先判断是否超卖、是否有系统异常，再比较 QPS、P95、P99。如果任一方案超卖或出现系统异常，本轮对比就不能作为优化结论。这样能避免只拿单个 QPS 数字讲优化。
