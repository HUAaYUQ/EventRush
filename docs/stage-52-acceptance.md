# Stage 52 验收：购票平台用户旅程重构

## 做了什么

- 购票端只保留“发现活动”和“我的票务”两个一级导航，不展示验票、运营和工程证据入口。
- 新增活动目录 `/`、活动详情 `/events/:eventId`、结算 `/checkout`、票务中心 `/account` 四种独立页面。
- 活动目录只负责搜索、售票状态筛选和进入详情；活动详情只负责查看信息、选择场次与票档。
- 结算页按订单状态一次只显示购票人核对、支付或候补结果，不再把全链路同时铺开。
- 我的票务使用“全部、待支付、候补中、待使用、售后、已完成”状态导航，以及列表与详情主从布局。
- 引入本地活动现场图，统一为冷灰白底、炭黑文字、朱红交易按钮；绿色只表示可售和成功。
- 保留 `/gate`、`/ops`、`/lab`、`/demo` 兼容访问，但它们不进入消费者产品导航。

## 你该学会什么

1. 产品导航按用户目标划分，不能按后端接口数量划分。
2. 活动目录、活动详情、结算和订单中心分别解决“找、选、买、管”，每屏只承担当前任务。
3. 12306 值得参考的是任务分区、待支付恢复和候补心智，不是复制它的视觉或铁路术语。
4. 状态导航和主从布局能让用户处理一条订单，而不是被候补、订单、电子票和退票模块同时淹没。
5. 接口缺少价格时应显示“票价待确认”，不能把未知数据伪装成 `¥0.00`。

## 页面验收

1. 打开 `/`，确认只看到活动搜索、筛选和活动卡片，看不到购票人、支付、退票或工程信息。
2. 打开 `/events/1`，确认左侧是活动内容，右侧只选择场次与票档；移动端变为单列。
3. 从详情进入 `/checkout`，确认未下单时只显示购票人和订单核对，创建订单后只显示支付。
4. 打开 `/account`，切换六个状态，确认列表与当前详情构成主从关系，没有把所有详情纵向铺开。
5. 打开 `/my`，确认自动跳转 `/account`。
6. 确认消费者顶部导航看不到验票、平台运营、压测或工程证据入口。
7. 用 320、375、414、768 和 1365 像素宽度检查 `/`、`/events/1`、`/checkout`、`/account`，确认无横向溢出。

## 面试表达

> 我没有继续在一张页面里堆功能，而是围绕购票用户的四个真实目标重构信息架构：先发现活动，再选择场次和票档，随后进入独立结算，最后在状态化票务中心恢复待支付、候补、电子票和售后。高并发后端能力仍然保留，但消费者界面只呈现完成任务所需的信息。
